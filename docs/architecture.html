Orkestra: architecture and flow

Orkestra is a plugin for Claude Code, Cursor and GitHub Copilot: it takes a development request through discovery, questions, a plan, your approval, test-first implementation, verification, review and delivery. It does not leave the rules to the model's goodwill; a command line tool and hooks enforce them.

What it does

  • You write the request: /orkestra:run add CSV export to the shop
  • It learns the project, asks only the questions that change the outcome, and writes spec.md and plan.md.
  • Not one line of source code can be written until the plan is approved.
  • Every task is closed with evidence of a failing test first and a passing test after.
  • Every check that passed at the start (tests, lint, types, build) must still pass at the end.
  • After an independent review and an adversarial test it writes the report and updates the project memory.
  • It speaks two languages: output, document templates and --help are English or Turkish (orkestra lang).

What it does not do

  • It does not commit, push, branch or open a PR unless you ask for it in that very message.
  • It does not run deploys, store uploads or production database changes.
  • It does not read or write .env and key files.
  • During a run it does not write to another project and does not install unapproved packages.
  • It does not promise 100% correctness: the aim is that a gate, a hook or a review catches the mistake before it reaches the codebase.
  • It does not supervise tools other than Claude Code, Cursor and Copilot; in Cursor only the chats that carry an orkestra run. See Three engines and Scope.

Architecture

Four parts work together: the orchestrator (the run skill) drives the work, the CLI keeps state and evidence, hooks check every tool call, and the agent team does the pieces of the job. State lives in files, not in the model's memory.

Hooks fail open (Claude Code and Cursor): if an error occurs inside dispatch.py the session is not locked, the error is written to ~/.orkestra/logs/hooks.log and the tool call is allowed. This keeps a guard error from stopping your work; the price is that the guard did not run at that moment. In Copilot, PreToolUse fails closed: if the hook crashes or the payload is invalid, the tool call is denied. Cursor and Copilot events are translated to the same handlers by cursor_hook.py and copilot_hook.py.

Three engines: Claude Code, Cursor and Copilot

A run is driven by Claude Code (the default), by Cursor (since 1.5.0) or by GitHub Copilot; you choose when you give the request. The state machine, gates, evidence and guards are one: there is no copy per engine, only one translator each for Cursor and Copilot events that feeds the same handlers (hooks/cursor_hook.py, hooks/copilot_hook.py).

Behaviors measured in Cursor that shaped the design

  • Every subagent is a separate chat and its events carry no agent type: the main session's Task call is recorded, the subchat is matched by the text of its first message; its first calls arrive before the transcript exists and are judged by the role of the pending launch.
  • There is no AskUserQuestion: the question and the plan approval happen as text in the chat (orkestra await, you write approve, the hook records it).
  • In print mode (agent -p) no prompt or stop event arrives: the bridge and the watchdog report the prompt to the hook layer themselves.
  • The shell keeps its directory between calls but does not report it in the event: cd is tracked command by command; if it cannot be tracked, the next command has to start with an absolute cd.
  • A command that exits non-zero ends with a separate event (postToolUseFailure); there is no event for a subagent finishing, the return is inferred from the main session's next move.

Installation and limits

  • orkestra cursor install: links skills and subagents into ~/.cursor, adds hook entries to ~/.cursor/hooks.json without touching your entries (backup first), puts the orkestra command on PATH. uninstall undoes it.
  • Cursor chats unrelated to an orkestra run are left alone. A chat that carried a run stays subject to the git / secrets / store rules after the run closes. For all Cursor chats: engine.cursor.global_guards.
  • Without the hooks installed, the bridge and the watchdog do not start a Cursor turn; orkestra start also does not work in a chat the hooks cannot see.
  • Tried with the command line tool on five real runs; the IDE window was not tried separately. There is no token counting for Cursor runs and no TDD warning for the implementer at finish time.
  • Self-approval: in one trial the model ran the hook script itself and approved its own plan instead of waiting for approval. It was closed (command and file content checks + the hook recognizing that an agent started it + an explicit prohibition text), but the guards are not a sandbox.
  • Copilot: orkestra copilot install writes the hook entries; you enable the Orkestra agent plugin and the SessionStart, UserPromptSubmit, PreToolUse, PostToolUse hooks in the host (VS Code or Copilot CLI) yourself. A Copilot session without hooks must not start a guarded run. Copilot CLI launches default to the model gpt-6-luna with reasoning effort max.

If a task review is PASS the task closes; minor notes do not reopen it, they move to the final review. FAIL reopens the task; if the same task gets a third FAIL, the decision is put to you. At every step orkestra next names the single next job (see Tempo and resume).
The places where you intervene: the clarifying questions and the plan approval. Everything in between is autonomous. Commit and push are not part of the flow; they happen only if you call /orkestra:ship or ask for them explicitly in that message.

Guards: rules enforced by hooks

There are two layers. The first runs in every session where the plugin is loaded. The second applies only in a session bound to a run. Nine guards (git, secrets, store, isolation, deploy, deps, phase, wait, dialogs) can be switched off one by one in ~/.orkestra/config.json.

In every session with or without a run

  • git: add, commit, push, branch, merge, reset, stash run only if explicitly requested in that message; the permission does not carry over to the next message. --no-verify, force-push to main and git config changes never run.
  • secrets: .env*, *.p8, *.pem, service-account JSON files, .npmrc with tokens etc. cannot be read, written or moved.
  • store: eas build (non-local), eas submit, eas update, expo publish are blocked.
  • home: ~/.orkestra cannot be changed by the model.
  • rollback: orkestra rollback --yes only on your explicit request.
  • complex: a command with more than 200 distinct redirect targets or more than 2000 commands, or one whose check does not finish within the hook's deadline (6 s of CPU, 9 s of wall clock), is rejected. Reason: a hook that times out leaves the command unchecked.

Only during a run in the bound session

  • phase: source code cannot be written before the plan is approved.
  • isolation: no writing outside the run's project (temporary folders excepted).
  • deps: no package that the plan did not approve can be installed.
  • deploy: deploy, publish, production migration, ssh and remote rsync do not run.
  • destructive: recursive deletion (rm -r) with targets it cannot name, or anywhere but a dedicated temporary subfolder, does not run.
  • roles: read-only agents write only their report; the implementer cannot use the orchestrator's commands.
  • internals: no hand-written or scripted writes to machine state (.orkestra/runs); reading evidence and activity logs is allowed; after approval spec.md is frozen; the model cannot embed an answer anywhere in an approval question.
  • wait: the main session cannot run sleep or a polling loop to wait for a subagent; it cannot poll the run's files in a loop.
  • dialogs: commands that open a macOS system window on your screen (keychain password prompt, osascript dialog, xcode-select --install) do not run.
  • Stop: if the model tries to end the turn while a run is active, it is continued by naming the next step (at most 2 times per message). If a subagent is running in the background or its report is on the way, the turn may end; the report arrives as a new message and continues the flow.
How command lines are read: the guard reads orkestra … lines with the CLI's own parser, so what the guard sees is what runs (no option abbreviations). The command behind orkestra tdd and orkestra evidence passes the same guards. Redirections with no program (exec 3>file, > file) count as writes. Paths are compared case-insensitively (macOS disks do not distinguish case). Below /tmp/<folder> is deliberately exempt from isolation; the root itself (/tmp/*) is not.

Tempo and resuming without a break

In the records of the five runs on 4-5 October, 12-34% of the wall clock was spent as "subagent finished, main session still in a waiting command". 1.4.0 removes that wait and makes the sub-step an interrupted run continues from computable from files.

How the wait went away

  • Claude Code runs subagents in the background; the report reaches the main session as a new message. Before, the Stop hook prevented the turn from ending, so the model waited in a sleep loop.
  • Hooks write every background agent they start to .orkestra/runs/<run>/agents.json. While an agent runs the turn may end; when the report arrives, the hook adds the next step to the message.
  • The record cannot park a run: it drops when the report arrives and when a session restarts; if there is no subagent trace for 10 minutes it does not count (next names the normal step and leaves a note).
  • Report messages do not count as user messages: they give no approval, no rejection and no git permission.
  • In headless work (claude -p, bridge) the process ends with the turn, so the waiting is done inside the turn.

Resuming where it stopped

  • orkestra next gives the single next step. The task's sub-step (started · red exists · green is stale · waiting for review · review FAIL round N · review PASS) is derived from the state, the evidence and the review file; there is no separate "where was I" record.
  • The same state always gives the same answer: a task with evidence is not rewritten, the decision in the file is applied, questions and approvals are never answered for you.
  • Session start, resume, context, status, the Stop message and the arrival of a report use the same computation.
  • Calling task start and task done again writes nothing twice.

Evidence layer and gates

The sentence "I did it, I tested it" does not count as evidence. The CLI produces and stores the evidence; the model only runs the command.

Gates

  • orkestra init finds the project's test, lint, type check and build commands and writes them to .orkestra/config.json.
  • baseline: all of them run at the start of the run. Those that are already broken are recorded and not held against the run.
  • verify: run again at the end. A gate that passed at the start and is broken at the end counts as a regression and the review phase cannot be entered.
  • If the project has no tests, this net does not exist either; the report writes that down as a risk.

Test-first (TDD) and integrity

  • orkestra tdd red and tdd green run with the same command; if the test changes after red, green is refused (a justified --why goes into the report).
  • Deleted tests, added skip/only/xfail, @ts-ignore, eslint-disable are scanned; an exception is valid only if it is written in the approved plan.
  • verification.md cannot cite a file or test name that does not exist.
  • The CLI writes the evidence section of the report; if it is edited by hand, the closing is refused.
  • A backup of every changed file from before the run is kept; /orkestra:rollback restores them without touching git.

  • An old orkestra copy also answers in Cursor. Cursor also loads the copy (1.0.0) in Claude Code's plugin registry; that copy answers in Cursor chats with the old rules. orkestra cursor status shows it; claude plugin update orkestra@orkestra-local refreshes it (its effect on Claude Code was not tried).
  • Self-approval. Seen in a real run and closed with three layers; a script that cleans its environment, detaches from its parent processes and hides names can still get around it. On the Claude Code side the hook has no "an agent started me" check.
  • The scope gaps remain. A request typed without starting a run is not forced into the flow; a session not bound to the run can change source files; tools other than Claude Code, Cursor and Copilot are out of scope.
  • The wait guard is a nudge, not a security boundary. It does not catch indirect waits such as S=120; sleep $S.
  • Variable and expansion indirection. Guards read the command without running it; they cannot see a command stored inside $X. This was already so in 1.3.0.
  • The watchdog does not run by itself. If the bridge is running it runs it; if not, you have to set it up with orkestra watchdog --launchd.
  • Windows is less exercised. It is supported natively, but the maintainers have no Windows machine; the watchdog only notifies there and the Windows paths are covered by simulation and CI.
